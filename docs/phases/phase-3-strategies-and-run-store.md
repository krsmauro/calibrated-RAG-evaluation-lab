#### 3.2 [x] S3: Reciprocal Rank Fusion
Claimed: Claude (Opus 5.5, VS Code session), 2026-10-28
- **Do:** RRF over S1 and S2 rankings, smoothing constant as a parameter (start at the commonly used default; tune on dev only).
- **Verify:** Hypothesis tests: duplicates, ties, permutation of input order, empty input from one side. Hand-computed fixture.
- **Refs:** Design §7, §9 (Testing).
- Note (2026-10-28, from 3.1): the empty side is real, not only a test case: S1 returns only chunks that share a word with the query, fewer than 10 for 500 of 5,458 dev queries and none for 13. Decide how deep each side's list is (fusing two top-10 lists is not the same as fusing two top-100 lists) and treat that depth as a parameter. S1 is now the strongest single strategy on dev (F-011), so S3 has to beat S1, not just S2. Dispatch is a `match` on `strategy` in `service/routes.py`; pyright flags a missing case.
- **Done:** 2026-10-28, Claude (Opus 5.5, VS Code session). `service/fusion.py` holds `rrf`, a pure function: 1 / (rrf_k + rank) summed per chunk with `math.fsum`, a chunk repeated within one ranking counted at its first position, ties ordered by position in the document, then chunk id. `/retrieve` takes `strategy: "hybrid"` (S3): S1 and S2 each return `fusion_depth` chunks, `rrf` fuses them, the top k come back with the dense side's `embedder_id`. `rrf_k` and `fusion_depth` are request fields, required for hybrid and rejected for the other strategies, with `fusion_depth` at least k, so a run always names and records them. The harness builds every request before sending any, so a bad parameter fails once, before any HTTP; `ragcalibrate run` gained `--rrf-k` and `--fusion-depth`, and the run manifest records both. Both parameters were chosen on dev among 30 settings: `rrf_k` 10, `fusion_depth` 100.
  Evidence: `uv run python scripts/measure_rrf.py` (fetches S1 and S2 top 100 once, fuses prefixes offline with the service's `rrf`, scores with the harness's `score`), recall@5 on dev, S1 0.560: depth 10 to 100 with `rrf_k` 60 gives 0.566 to 0.569; with `rrf_k` 10, 0.569 to 0.576; with `rrf_k` 1, 0.572 to 0.573; best depth 100 and `rrf_k` 10, recall@5 0.576, MRR@10 0.477, better than S1 on 583 queries and worse on 446. `uv run ragcalibrate run --strategy hybrid`: recall@5 0.576, MRR@10 0.477 (results ledger); a second run identical per query; per query equal to the offline fusion for all 5,458 queries. A check that the top 10 of a k = 100 response equals a k = 10 response held for all 5,458 dense queries. `make lint` clean; `make test` 82 passed (new: 5 hand-computed fusion fixtures, 5 Hypothesis properties: best-first order with the tiebreak, at most k unique chunks, permutation of the rankings, a ranking alone, with an empty side or fused with itself keeping its order, a repeat within a ranking changing nothing, a chunk appended to one ranking not reordering the others; 8 contract cases), also with `CI=1` (derandomized); `make test-integration` 41 passed (7 new: hybrid equals `rrf` over the two rankings, an empty fts side leaving dense's order, hybrid error cases). Mutation check: removing the tiebreak or the within-ranking dedupe fails tests; replacing `math.fsum` with `sum` does not (no rank combination in the tested range is order-dependent in floating point), and `fsum` is kept so the order-independence the property test asserts holds for any number of rankings.
  Files: `src/ragcalibrate/service/fusion.py` (new), `scripts/measure_rrf.py` (new), `tests/unit/test_fusion.py` (new), `tests/property/test_fusion_properties.py` (new), `src/ragcalibrate/contract.py`, `src/ragcalibrate/service/retrieval.py`, `src/ragcalibrate/service/routes.py`, `src/ragcalibrate/harness/run.py`, `src/ragcalibrate/harness/cli.py`, `tests/unit/test_contract.py`, `tests/integration/test_service.py`, `docs/results.md`, `docs/findings/F-011-fts-beats-dense-on-cuad-dev.md`, `README.md`, `.claude/skills/master-code-skill/SKILL.md`, `docs/project-plan.md`; for the S2 rounding correction also `docs/adr/0009-postgres-fts-is-not-bm25.md`, `docs/findings/F-004-ceiling-effect-per-document-retrieval.md`, `docs/findings/F-008-cuad-facts.md`, `docs/phases/phase-2-cuad-ingest-and-dense-retrieval.md`.
  Deviations: (1) two parameters, not one: the depth of each list is a parameter too, as the 3.1 note asked. (2) `rrf_k` is 10, not the common default 60: tuned on dev as the step allows; the default's number is in the results row. (3) S3 beats S1 by only 1.6 points on dev; written up as a note on F-011, not a new finding. (4) While checking numbers, S2's recall@5 turned out to be mis-rounded everywhere it was quoted (0.489; the exact mean is 0.48846): corrected to 0.488 in the ledger, the plan, ADR 0009, F-004, F-008, F-011 (whose S1 lead becomes 7.2 points, not 7.1) and the Phase 2 and 3 files. The S3 results row was measured on a dirty tree and should be rerun on the commit.

#### 3.8 [ ] Determinism test
- **Do:** make ranking deterministic: explicit tiebreak (for example by chunk id) after score sort, so equal scores cannot reorder between runs.
- **Verify:** run S1 to S4 twice; the `retrievals` tables are identical. If floating-point differences break exact equality for dense scores, record the tolerance in a finding and compare ranks, not raw scores.
- **Refs:** Design §11 (Week 3 exit).
- Note (2026-10-28, from 2.7): S2 already breaks ties by position (`ORDER BY score DESC, c.start_char` in `DENSE_SQL`). Use the same rule for the other strategies, RRF included, so ties sort the same way everywhere.
- Note (2026-10-28, from 3.1): S1 (`FTS_SQL`) uses the same tiebreak, and `ts_rank` produces many equal scores, so the tiebreak matters there. Two S1 runs on dev already gave identical rankings and scores.
- Note (2026-10-28, from 3.2): RRF (`service/fusion.py`) orders ties by fused score, then `start_char`, then chunk id, and sums with `math.fsum`, so a fused score does not depend on the order of the two lists. Two S3 runs on dev gave identical rankings and scores.
- Note (2026-10-28, from 3.3): S4's reordering (`rerank` in `service/rerank.py`) uses the same tiebreak (score, then `start_char`, then chunk id). Two S4 runs on dev gave identical rankings and scores. The cross-encoder scores a pair a little differently (at most 2.4e-6) depending on what it is batched with; within one service the batch for a query is always the same N candidates in the same order, so this does not show run to run, but it does between depths.
