#### 4.1 [x] Paired cluster bootstrap
Claimed: Claude (Opus 5.5, VS Code session), 2026-11-04
- **Do:** `stats/bootstrap.py`, pure functions, seeded RNG, no I/O. Input: per-query metric values for candidate and baseline, joined on `query_id`, with a cluster label (`document_id`). Resample clusters, take all queries of each sampled cluster, compute the mean paired difference. Percentile CI, 10,000 resamples by default. Seed is returned with the result. Use numpy (already needed); no new dependency.
- **Verify:** known-answer tests on tiny hand-computed inputs (for example two clusters, where the bootstrap distribution is enumerable); same seed gives the same CI; unpaired or mismatched query sets raise.
- **Refs:** Design §8.5; skill EVAL-CRITICAL-3.
- **Done:** 2026-11-04, Claude (Opus 5.5, VS Code session). `stats/bootstrap.py` holds `paired_cluster_bootstrap(candidate, baseline, cluster_of, *, seed, n_resamples=10_000, confidence=0.95)`: per-query values keyed by query id, each query's cluster (its document), and an `Interval` back (observed mean paired difference over queries, `lo`, `hi`, the numbers of queries and clusters, and the resamples, confidence and seed used). A resample draws as many clusters as there are, with replacement, and takes the mean difference over all their queries (so a cluster weighs by its number of queries); the interval is numpy's linear-interpolation percentiles of those means. Clusters are sorted before drawing, so the same seed gives the same interval whatever order the inputs come in. It raises for query sets that are not the same in both runs, a query with no cluster, a value that is not finite, fewer than two clusters, or settings out of range. The query-level bootstrap needed in 4.2 and 4.6 is the same function with each query its own cluster. A new import-linter contract keeps `stats/` from importing anything else in `ragcalibrate`.
  Evidence: `uv run pytest tests/unit/test_bootstrap.py`: 14 passed. Hand-computed: two clusters (differences +1 and 0 against -1) give exactly [-1, 0.5] at 95% and [0, 0] at 40%, since the bootstrap distribution is 1/4, 1/2, 1/4 on three values; three queries at +1 against one at 0 give a mean of 0.75 (not 0.5) and [0, 1]; a constant +0.25 shift over spread-out baselines gives [0.25, 0.25]. The same seed repeats the interval and a shuffled input order does too, another seed changes it; the vectorized resampling equals a plain loop over the same draws to 1e-12; with correlated clusters the clustered interval is more than twice as wide as the query-level one. Mutation check (bytecode cache off): 10 planted bugs (mean of cluster means, queries resampled instead of clusters, clusters in input order, unpaired queries dropped, one cluster allowed, seed ignored, 90% tails, the difference reversed, NaN allowed, an unweighted mean), all caught. The new contract breaks when a planted `ragcalibrate.harness` import is added to `stats/`. On the stored dev runs (ad hoc, not yet a command; that is 4.4), recall@5, seed 20261104: S3 - S1 +0.0158, 95% CI [+0.0054, +0.0265]; S1 - S2 +0.0716 [+0.0565, +0.0871]; S3 - S2 +0.0874 [+0.0775, +0.0973]; 408 documents, 5,458 queries; the clustered intervals are 1.09 to 1.21 times as wide as query-level ones. One bootstrap on all of dev takes 0.06 s and 63 MB. `make lint` clean; `make test` 194 passed.
  Files: `src/ragcalibrate/stats/bootstrap.py` (new), `tests/unit/test_bootstrap.py` (new), `pyproject.toml` (import-linter contract), this file.
  Deviations: (1) The step's `confidence` and `n_resamples` are parameters with the Design §8.5 defaults. (2) `Interval` is a `NamedTuple`, not a Pydantic model: it crosses no trust boundary. (3) The query-level variant on all of dev holds a 10,000 by 5,458 index array (about 1 GB at peak); on CI-sized subsets (4.6) it is small, so it was left unchunked. (4) The import-linter contract was not asked for; it enforces the skill's rule that `stats/` does no I/O and depends on nothing in the project.

#### 4.2 [x] Coverage test on synthetic data
Claimed: Claude (Opus 5.5, VS Code session), 2026-11-04
- **Do:** simulate data with a known true delta and within-cluster correlation. Check that about 95 percent of 95 percent intervals contain the truth for the cluster bootstrap, and show that the query-level bootstrap under-covers when clusters are correlated. Run it for several cluster counts, **including small ones** (about 20 to 40 contracts), because percentile bootstraps can under-cover with few clusters.
- **Verify:** test asserts coverage within a tolerance band computed from the number of simulations; the small-cluster result is recorded in a finding. If coverage is poor at the planned CI-subset size, record it and escalate (options: larger subset, BCa intervals, a t-based interval). Do not proceed on a silent shortfall.
- **Refs:** Design §8.5; finding F-003.
- **Done:** 2026-11-04, Claude (Opus 5.5, VS Code session). `stats/coverage.py` draws synthetic paired comparisons with a known true difference and 2 to 24 queries per contract, in two shapes: Gaussian with a chosen intraclass correlation (ICC), and a discrete null shaped like CUAD's recall@5 differences (mostly 0, a contract-level tilt up or down). `coverage()` counts how many 95% intervals hold the truth, and how many lie wholly below it (a false Fail when the truth is 0), for the cluster bootstrap and for the query-level one. `scripts/measure_coverage.py` prints the table for 10 to 200 contracts. Result (finding F-003, now confirmed): at dev's correlation the cluster bootstrap covers 91.5%, 92.1% and 93.3% at 10, 20 and 30 contracts, with false fails at 4.1%, 3.8% and 3.0%, and 94.6% to 95.2% from 40 contracts up; the query-level bootstrap covers 87% to 89% with 5.7% to 7.2% false fails at every size. Escalation, as the step asks: no CI-subset size is planned yet (4.5 is provisional, 4.6 sets it), so the shortfall is recorded as a constraint, at least 40 contracts and 60 for margin, rather than a problem at a chosen size. Nothing else blocks.
  Evidence: `uv run python scripts/measure_coverage.py --simulations 2000 --resamples 2000` (seed 42), table in F-003. Dev's ICC, measured on the stored runs, is 0.021 to 0.053; the discrete draw at strength 1.0 has 0.043. `uv run pytest tests/unit/test_coverage.py`: 5 passed (400 simulations per check, band ±3.29 binomial standard errors, ±0.036 around 95% and ±0.026 around a 2.5% tail): the cluster bootstrap within the band at 60 contracts with ICC 0.20 and at 100 contracts on the CUAD-shaped null, with its false-fail side within the band of 2.5%; the query-level one below the band and more than 10 points below the clustered one; counts reproducible from the seed; the synthetic data's ICC within 0.03 of the one asked for. `make lint` clean; `make test` 225 passed in about 5 s.
  Files: `src/ragcalibrate/stats/coverage.py` (new), `scripts/measure_coverage.py` (new), `tests/unit/test_coverage.py` (new), `docs/findings/F-003-few-clusters-bootstrap-coverage.md`, this file, `docs/project-plan.md`.
  Deviations: (1) The simulations use 2,000 resamples per interval, not the gate's 10,000, to keep the table to minutes; the count of resamples hardly moves coverage at this level, but it was not checked separately. (2) With strong within-contract correlation (Gaussian, 0.20) the cluster bootstrap stays a little short even at 60 to 200 contracts (93.6% to 94.3%); dev's correlation is far lower, and 4.6 measures the real rate. (3) The query-level rows stop at 100 contracts: each query is its own cluster, which is slow, and the point is made.

#### 4.3 [x] Gate decision function
Claimed: Claude (Opus 5.5, VS Code session), 2026-11-04
- **Do:** `stats/gate.py`: given `[lo, hi]` and δ, return Pass, Fail or Inconclusive per the rule in Design §8.5, including the "small regression detected" note. Holm-Bonferroni helper only if more than one metric gates (default: one primary metric).
- **Verify:** property tests on every boundary (`lo == -δ`, `hi == 0`); exhaustive table test of the three outcomes.
- **Refs:** Design §8.5.
- **Done:** 2026-11-04, Claude (Opus 5.5, VS Code session). `stats/gate.py` holds `decide(lo, hi, delta) -> Decision`: an `Outcome` (`pass`, `fail`, `inconclusive`, a `StrEnum` so a report prints the word) and a `small_regression` flag, set only on a Pass whose interval lies wholly below zero. Pass is `lo >= -delta`, Fail `lo < -delta and hi < 0`, Inconclusive `lo < -delta and hi >= 0`, as in Design §8.5. It raises for `lo > hi`, a negative delta, or a value that is not finite. No Holm-Bonferroni helper: one primary metric gates (the step's default).
  Evidence: `uv run pytest tests/unit/test_gate.py tests/property/test_gate_properties.py`: 25 passed. A table of 17 hand-written cases covers each outcome and every boundary (`lo == -delta` passes; `hi == 0` is Inconclusive below `-delta` and a Pass without the note above it; zero-width intervals at and just past `-delta`; delta 0), plus four invalid inputs. Hypothesis, on any interval in [-1, 1] and delta in [0, 0.5]: exactly one of Design §8.5's three conditions holds and it is the outcome; moving the interval up never gives a worse outcome (Fail, then Inconclusive, then Pass), nor does a larger delta. Mutation check: 8 planted bugs (a strict `lo > -delta`, Fail on `hi <= 0`, no note, the note on `hi <= 0`, Inconclusive collapsed into Pass, the sign of delta flipped, `lo > hi` or a negative delta accepted), all caught. `make lint` clean.
  Files: `src/ragcalibrate/stats/gate.py` (new), `tests/unit/test_gate.py` (new), `tests/property/test_gate_properties.py` (new), this file.
  Deviations: (1) No minimum number of clusters in the rule: the stats rules (STAT-HIGH-2) want too few clusters to give Inconclusive with a reason, and 4.2 measures where the bootstrap's coverage breaks down; the guard belongs with `compare` (4.4), once 4.2 gives the number. (2) Done before 4.2, which it does not depend on.

#### 4.6 [ ] Subsampling study: false alarms, power, MDE
- **Do:** treat all of dev as the population, run each configuration once on all of dev, then draw 1,000 random CI-sized subsets of contracts and apply the gate to each using only stored results.
  1. False-alarm rate for two configurations with about zero full-dev delta, with query-level and cluster-level resampling side by side.
  2. Power: seed regressions of known size (for example drop the relevant chunks from the top k on a random p percent of queries) and plot the share of subsets that Fail against the size. Read off the minimum detectable effect.
  3. Use the power curve to set the CI-subset size and δ. The size comes from this, not from a guess.
- **Verify:** script plus output committed (or regenerable by one command); numbers in `docs/results.md`; a finding states the chosen subset size and δ with the evidence. Watch for ceiling effects (F-004): if recall@5 is near 1.0, power on it will be poor and another primary metric or k may be needed.
- **Refs:** Design §8.5; findings F-003, F-004.
